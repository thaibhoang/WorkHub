# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WorkHub is an agent factory: Claude agents take tasks through triage → spec → implement → review → verify → ship, every step is recorded as an event, and the metrics derived from those events (cost, duration, failure rate, rework loops, human interventions) feed a self-improvement agent that proposes changes to the workflow. The full design (in Vietnamese) is in `docs/architecture.md`. Read the relevant section before building a new component, and update the doc when the implementation diverges from it. The design is modelled on Warp's Factories product.

Status: **Phase 0–6 done**: event store, projections, Claude Code runner with retries, factory-as-code, the Foreman pipeline with gates, rework loops, and crash recovery, the axum API + SSE with the React/shadcn UI, LLM-as-judge scorers, the self-improvement agent (proposals → human review → rollout → before/after by factory_version), and benchmarks (fixed suites with hidden checks run against a factory at a git ref, proposal vs base comparison). Next is Phase 7 (integrations, Docker sandbox). See the roadmap in the architecture doc, §8.

Decided stack: Rust backend, React + TS + shadcn/ui in `web/`, local-only deployment, tasks created via WorkHub/CLI/UI, git worktree as the agent sandbox.

cargo run --bin wh -- bench suites | runs | show <run> | compare <a> <b>
cargo run --bin wh -- bench run <suite|file> [--ref R | --proposal P] [--repeat N] [--case id]   # runs inline (real agents, real cost)
cargo run --bin wh -- bench worker                                   # runs benchmarks queued from the UI/API
cargo run --bin wh -- gate approve|reject <task> [--comment ...]
cargo run --bin wh -- task show|resume|cancel <task>

Integration tests use `#[sqlx::test(migrator = "wh_eventstore::MIGRATOR")]`. Each test gets a fresh throwaway database created from `DATABASE_URL`.

## Architecture (event sourcing + CQRS)

- **`crates/wh-core`**: pure domain types, no I/O. Typed IDs (`TaskId` etc.) map to stream ids `"<prefix>-<uuidv7>"`. `EventMeta` holds `correlation_id` (= task id), `causation_id`, `actor`, and `factory_version`. Domain events are internally tagged serde enums (`#[serde(tag = "type")]`) that implement `DomainEvent`. The payload's `type` must equal `event_type()`. `FailureClass` is the fixed failure taxonomy.
- **`crates/wh-eventstore`**: `events` is append-only (a DB trigger blocks UPDATE/DELETE). `append` takes a **global advisory lock**, so `global_seq` order equals commit order. That is what makes `read_all(after_seq)` with per-consumer `consumer_checkpoints` safe. Don't remove the lock without replacing that guarantee. `ExpectedVersion` gives optimistic concurrency per stream. Each append fires `NOTIFY wh_events`.
- **Consumers** implement `EventHandler` and are driven by `Subscription::catch_up` / `run`. Delivery is **at-least-once**, and the checkpoint is saved after each batch, so handlers must be idempotent. Projections do this by storing `last_seq` per row and ignoring events with a seq at or below it.
- **`crates/wh-metrics`**: read-model projections (implement `Projection` so `rebuild` can truncate and replay). Read-model tables live in `migrations/` alongside the event tables. They are disposable and must be fully derivable from events.
- **`crates/wh-runner`**: `Runner` executes one agent session. It creates a git worktree at `$WH_DATA_DIR/worktrees/<session>` (default `~/.local/share/workhub`), drives an `AgentRuntime`, and records `SessionEvent`s. The task stream gets `StageEntered`/`StageExited`. Runtimes never return `Err`: every failure becomes an `Outcome` with a `FailureClass`, so it shows up in metrics. `claude_code::ClaudeCode` spawns `claude -p --output-format stream-json` with `--strict-mcp-config` (user MCP servers are skipped unless `--with-user-mcp`) and `--max-budget-usd`, and writes the raw transcript to `transcripts/<session>.jsonl`. `StreamParser` is pure and unit-tested. Retries: `RunSpec.max_retries` (CLI `--max-retries`, default 2, so at most 3 runs) applies only to `retryable` failures (timeout, unknown). Budget and env_setup failures are not retried. Each attempt is a new session with a fresh worktree, linked by `attempt`/`retry_of` on `AgentDispatched`. The task stream still gets one `StageEntered` and one final `StageExited`. Runner tests use a fake runtime and a temp git repo.
- **`crates/wh-factory`**: loads `factory.yaml` (`deny_unknown_fields`). Agent prompt paths and `repo` are relative to the factory file. `version` is a sha256 over the yaml plus all agent prompts and is stamped as `factory_version` on every pipeline event. `factory/` holds WorkHub's own factory (dogfooding).
- **`crates/wh-foreman`**: process manager. On each task event it folds `TaskState` (in wh-core) from the full stream, acts only if the event is the stream head and the task's `factory` matches, then calls the pure `decide(state, factory)`. Every action is appended with `Exact(state.version)`, and the runner's `StageEntered` uses `RunSpec.task_expected_version`, so redelivery never double-dispatches. A conflict means someone else acted first and is ignored. All stages of a task share branch `wh/task/<id>`, and the runner commits on success so later stages see earlier work. A stage with `on_reject` must end with `VERDICT: APPROVE|REJECT` (`parse_verdict`). REJECT sends the task to the `on_reject` stage with the summary as feedback, up to `max_rework_loops`, then it is blocked. `recover_interrupted()` runs at foreman startup: it blocks tasks left at `StageEntered` and fails their orphaned sessions. `Dispatch::Inline` is used in tests, `Spawn` in the daemon.
- **`crates/wh-scorer`**: `ScorerService` consumes session completions and grades sessions of each factory scorer's `target` agent (only for tasks of that factory, deterministic `sampling_rate`). The judge is the same `AgentRuntime` (Claude Code) run with `AgentRequest.tools = Some(vec![])` in a temp dir. `judge.rs` is pure and unit-tested: it builds the prompt from rubric + task + agent prompt + final message + `git show <commit>` + condensed transcript, and parses the trailing JSON `{"score","classification","rationale"}`. WorkHub computes `pass` from `pass_threshold`. Events go on `score-<id>`: the automatic id is UUIDv5(session, scorer) and `ScoreStarted` is appended with `NoStream`, so redelivery never grades twice. `wh score session` uses a fresh id (`manual`). On first start the consumer checkpoint jumps to the log head (no paid backfill), and `recover_interrupted()` fails dangling `ScoreStarted`. Scorer prompts are hashed into `factory_version`. Read model `score_results` (`wh_metrics::scores`).
- **`crates/wh-improver`**: self-improvement. Runs are requested by `ImprovementRequested` on `proposal-<id>` (human via CLI/API, or `tick()`: factory `improvement.triggers` once per (trigger, factory_version) and `interval_hours` when there are ≥ `min_sessions` new sessions, both with deterministic `ProposalId::for_key` ids + `NoStream`, capped by `max_open_proposals`). `ImproverService` (consumer `improver:<factory>`) claims a request with `ImprovementStarted` at `Exact(1)` (at most once), builds the observation (`observe.rs`: per-version/stage metrics from read models, failures, scorer findings, review/gate/block feedback text from task streams, past proposals with reviewer comments, condensed example transcripts), and runs Claude Code (`acceptEdits`) in a worktree of the factory's git repo on branch `wh/proposal/<id>`. It may only edit files under the factory file's directory; WorkHub then requires the answer JSON (`prompt.rs`, pure + unit-tested), validates `Factory::load` on the worktree, requires a changed `factory_version`, commits, and records `ProposalCreated` (diff, files, proposed version) or `ImprovementSkipped`/`ImprovementFailed` (branch deleted). `commands.rs` (shared by CLI/API): `decide` (reject needs a comment, which the improver reads next time), `apply` (cherry-pick onto the factory repo's current branch, then `ProposalRolledOut`); `detect_rollouts` marks approved proposals live when the loaded factory has their version (hand-merged). A running foreman keeps the old factory until restarted. Read model `proposals_view`; `session_facts.stage_outcome` (from `StageExited`) gives reject rates; `wh_metrics::proposals::version_stats` is the before/after view. Integration tests use a fake runtime that edits the worktree.
- **`crates/wh-bench`**: benchmarks. A suite (`benchmarks/*.yaml`, `suite.rs`, pure + unit-tested) lists cases: a task, where agents work (the factory repo, another `repo`, or a `fixture` dir copied into a fresh git repo per case run), and a `check` run with `sh -c` on the finished task branch (exit 0 = pass, env `WH_BENCH_SUITE_DIR`/`WH_BENCH_CASE` so hidden checks live in `benchmarks/checks/`). Suites live outside `factory/` so the improver cannot edit the yardstick. A run (`bench-<id>`) loads the suite's factory at a `git_ref` (detached worktree under `$WH_DATA_DIR/bench/<run>/`), creates each case as a task with `TaskCreated.benchmark` set, and drives it inline with `Foreman::for_benchmark` + `drive()` (gates auto-approved, reviewer `benchmark`). The live foreman ignores benchmark tasks (`Scope`). Claim/recovery follows the improver: `BenchmarkRequested` then `BenchmarkStarted` at `Exact(1)`; `wh bench run` appends both at once. `BenchmarkStarted.pid` keeps startup recovery away from runs of a live process. **Benchmark data must stay out of production metrics**: `AgentDispatched.benchmark` → `session_facts.benchmark_run` / `tasks_view.benchmark_run`, and every live aggregate (dashboard, stats, `version_stats`, improver observe/triggers) filters `benchmark_run IS NULL`. Scorers skip benchmark sessions. Add that filter to any new live query. Read model `benchmark_runs` + `benchmark_cases` (`wh_metrics::benchmarks`).
- **`crates/wh-api`**: axum API under `/api`. Human commands (create, gate, resume, cancel) live in `wh_api::commands` and are shared with the CLI: they validate against the folded `TaskState` and append with `Exact(version)`, so a stale decision returns 409. Reads come from `wh_metrics::queries` (projections), except task/session event timelines, which read the stream directly. `Live` + `/api/events/stream` is the SSE feed: one LISTEN task publishes the head `global_seq` on a `watch` channel, and each client keeps its own cursor and reads the log itself (supports `Last-Event-ID`, `?after=`, `?task=`). Bound to localhost with no auth. Tests drive the router with `tower::ServiceExt::oneshot`.
- **`web/`**: React 19 + Vite + Tailwind v4 + shadcn/ui (add components with `npx shadcn@latest add <name>`), TanStack Query, react-router. One `EventSource` (`src/lib/live.tsx`) invalidates queries on each event. Types for API responses live in `src/lib/api.ts`; keep them in sync with `crates/wh-api/src/dto.rs` and `wh_metrics::queries`.
- **`crates/wh-cli`**: the `wh` binary. Writes go through `EventStore::append` (commands → events). Reads come only from projections.
- The `wh` CLI pool allows 20 connections because every following consumer (5 projections, SSE, foreman, scorer, improver, bench worker) holds a LISTEN connection; adding consumers to `wh serve`/`foreman` may need more.
- `migrations/` is embedded at compile time via `wh_eventstore::MIGRATOR`. Add new files and never edit applied ones. After adding a migration, run `cargo build` then `wh db migrate` before running other commands. Otherwise projections fail with "column does not exist". New fields on existing events need `#[serde(default)]` so old events still decode.

New components from the design (foreman, runner, scorer, improver, api) become new `crates/wh-*` crates following the same pattern: consume events through `Subscription`, emit events through `EventStore`.
