# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

WorkHub is an agent factory: Claude agents take tasks through triage → spec → implement → review → verify → ship, every step is recorded as an event, and the metrics derived from those events (cost, duration, failure rate, rework loops, human interventions) feed a self-improvement agent that proposes changes to the workflow. The full design (in Vietnamese) is in `docs/architecture.md`. Read the relevant section before building a new component, and update the doc when the implementation diverges from it. The design is modelled on Warp's Factories product.

Status: **Phase 0–8 done**: event store, projections, Claude Code runner with retries, factory-as-code, the Foreman pipeline with gates, rework loops, and crash recovery, the axum API + SSE with the React/shadcn UI, LLM-as-judge scorers, the self-improvement agent (proposals → human review → rollout → before/after by factory_version), benchmarks (fixed suites with hidden checks run against a factory at a git ref, proposal vs base comparison), the Docker sandbox (agents run in a container over their worktree, configured per agent), and local-only GitHub integration (ship pushes the task branch and opens a PR via `gh`, PR reviews/CI/merge are polled and recorded as events, changes requested or failed CI sends the task back, tasks from labelled issues, PR cycle times). Phase 8 was verified on a real test repo (issue → PR → CI failure → rework → merge); the changes-requested path has only been tested with a fake `gh`, since GitHub does not let a PR author request changes. WorkHub's own factory (`factory/`) now ships to GitHub with a ship gate, and CI (`.github/workflows/ci.yml`: clippy, tests, web build) checks every PR; dogfooding runs locally (the production server is too small to build Rust). Next is phase 9 (Slack/Linear, NATS).

Decided stack: Rust backend, React + TS + shadcn/ui in `web/`, local-first (optionally deployed behind login at workhub.buihoangthai.com, see `deploy/README.md`), tasks created via WorkHub/CLI/UI, git worktree as the agent sandbox (optionally with a Docker container on top).

## Architecture (event sourcing + CQRS)

- **`crates/wh-core`**: pure domain types, no I/O. Typed IDs (`TaskId` etc.) map to stream ids `"<prefix>-<uuidv7>"`. `EventMeta` holds `correlation_id` (= task id), `causation_id`, `actor`, and `factory_version`. Domain events are internally tagged serde enums (`#[serde(tag = "type")]`) that implement `DomainEvent`. The payload's `type` must equal `event_type()`. `FailureClass` is the fixed failure taxonomy.
- **`crates/wh-eventstore`**: `events` is append-only (a DB trigger blocks UPDATE/DELETE). `append` takes a **global advisory lock**, so `global_seq` order equals commit order. That is what makes `read_all(after_seq)` with per-consumer `consumer_checkpoints` safe. Don't remove the lock without replacing that guarantee. `ExpectedVersion` gives optimistic concurrency per stream. Each append fires `NOTIFY wh_events`.
- **Consumers** implement `EventHandler` and are driven by `Subscription::catch_up` / `run`. Delivery is **at-least-once**, and the checkpoint is saved after each batch, so handlers must be idempotent. Projections do this by storing `last_seq` per row and ignoring events with a seq at or below it.
- **`crates/wh-metrics`**: read-model projections (implement `Projection` so `rebuild` can truncate and replay). Read-model tables live in `migrations/` alongside the event tables. They are disposable and must be fully derivable from events.
- **`crates/wh-runner`**: `Runner` executes one agent session. It creates a git worktree at `$WH_DATA_DIR/worktrees/<session>` (default `~/.local/share/workhub`), drives an `AgentRuntime`, and records `SessionEvent`s. The task stream gets `StageEntered`/`StageExited`. Runtimes never return `Err`: every failure becomes an `Outcome` with a `FailureClass`, so it shows up in metrics. `claude_code::ClaudeCode` spawns `claude -p --output-format stream-json` with `--strict-mcp-config` (user MCP servers are skipped unless `--with-user-mcp`) and `--max-budget-usd`, and writes the raw transcript to `transcripts/<session>.jsonl`. `StreamParser` is pure and unit-tested. Retries: `RunSpec.max_retries` (CLI `--max-retries`, default 2, so at most 3 runs) applies only to `retryable` failures (timeout, unknown). Budget, env_setup and usage_limit failures are not retried (`usage_limit` = Claude Code's "You've hit your … limit"; it is also left out of failure rates in improver observe and `version_stats`). Each attempt is a new session with a fresh worktree, linked by `attempt`/`retry_of` on `AgentDispatched`. The task stream still gets one `StageEntered` and one final `StageExited`. Runner tests use a fake runtime and a temp git repo. **Docker sandbox** (`docker.rs`): when `RunSpec.sandbox` is `Sandbox::Docker`, the worktree is still created and committed on the host. `docker::prepare` mounts it at the same path (rw), the repo's common git dir read-only and the worktree's own git dir rw (agents can read history but only WorkHub commits), plus a throwaway home `$WH_DATA_DIR/sandbox-home/<session>` (credentials copied there only when no auth env var is set; removed after the session). The container runs as the worktree owner's uid:gid. `ClaudeCode` wraps its args in `docker run` (`run_args` is pure and unit-tested). Auth and `env` variables are passed by name only. Exit 125–127 without a result = `env_setup`. On timeout or cancel the container is `docker rm -f`'d, since killing the client doesn't stop it. `AgentSessionStarted.sandbox` records the config (`session_facts.sandbox`).
- **`crates/wh-factory`**: loads `factory.yaml` (`deny_unknown_fields`). `env:` (in `defaults` or per agent, merged by key, leading `~/` = `$HOME/`) is set on the agent process (`RunSpec.env` → `AgentRequest.env`) and passed into a docker sandbox by name; the dogfood factory uses it for a shared `CARGO_TARGET_DIR`. `tools:` (in `defaults` or per agent) restricts the built-in tool set (`RunSpec.tools` → `--tools`; unset = all tools); the dogfood factory uses it because every tool definition is resent each turn. `sandbox:` (in `defaults` or per agent; an agent's block replaces the default block as a whole) resolves to `wh_core::Sandbox`. Volume host paths are made absolute at load. Agent prompt paths and `repo` are relative to the factory file. `version` is a sha256 over the yaml plus all agent prompts and is stamped as `factory_version` on every pipeline event. `factory/` holds WorkHub's own factory (dogfooding).
- **`crates/wh-foreman`**: process manager. On each task event it folds `TaskState` (in wh-core) from the full stream, acts only if the event is the stream head and the task's `factory` matches, then calls the pure `decide(state, factory)`. Every action is appended with `Exact(state.version)`, and the runner's `StageEntered` uses `RunSpec.task_expected_version`, so redelivery never double-dispatches. A conflict means someone else acted first and is ignored. All stages of a task share branch `wh/task/<id>`, and the runner commits on success so later stages see earlier work. A stage with `on_reject` must end with `VERDICT: APPROVE|REJECT` (`parse_verdict`). REJECT sends the task to the `on_reject` stage with the summary as feedback, up to `max_rework_loops`, then it is blocked. `recover_interrupted()` runs at foreman startup: it blocks tasks left at `StageEntered` or `StageResumed` and fails their orphaned sessions. **Agent questions** (**off**: `PAUSE_ENABLED = false` until the real `claude --resume` is verified, see `docs/architecture.md` §5.3; tests use `Foreman::with_pause(true)`): a paused run → `AgentAsked` with the resume handle (reload + `Exact`, only while still `Running` that stage). `UserAnswered` sets `TaskState.resume_pending`, and `decide` returns `ResumeStage` from that flag, not the last event; the foreman appends `StageResumed` (`Exact`) before `Runner::resume`, building everything from events. Past the agent's `max_questions`, and in benchmarks, `AgentAsked` + an automatic `UserAnswered` (user `AUTO_ANSWER_USER`, not a human intervention) go in one append. A resume that is lost or fails blocks the task. `Dispatch::Inline` is used in tests, `Spawn` in the daemon. **Cleanup** (`cleanup.rs`, `wh cleanup`): `sweep` removes worktrees/sandbox homes of finished or orphaned sessions, scorer/bench leftovers, `wh/task/*` branches of merged (right away) or cancelled (after the grace period) tasks, and shared build caches over their size limit while nothing runs. With `github:` (`CleanupConfig.remote`) it also deletes those branches on the remote, plus, after the grace period, the remote branch of a PR closed without merging (the local one is kept: the task is blocked and resumable). Remote candidates come from `git ls-remote`, so failed deletes are retried; an already-gone branch is not an error; tracking refs are pruned with `git remote prune`. Deleting the branch of a cancelled task's open PR closes that PR. Otherwise never branches of locally completed, blocked or open tasks, and nothing outside `wh/task/*`. The daemon runs `run_janitor` at startup, when one of its tasks is done/cancelled (`with_janitor`), and every 30 min (`WH_CLEANUP_GRACE_HOURS`, `WH_CACHE_MAX_GB`, `WH_NO_CLEANUP=1`).
- **Agent databases** (`wh-foreman/src/task_db.rs`): agents never inherit `DATABASE_URL` or `WH_AGENT_DB_*` (`wh_runner::strip_live_env`, applied by `ClaudeCode::command` and benchmark checks; factory `env:` can still set `DATABASE_URL`). With `task_database: { admin_url_env: WH_AGENT_DB_… }`, the foreman creates `wh_task_<last 12 hex of the task id>` before a stage, migrates it once, and sets the session's `DATABASE_URL` and a temp `WH_DATA_DIR`; failure blocks the task with no session. Each database's comment holds the event store's id (`instance` table), and the janitor drops only its own, exactly-named ones: task done/merged, cancelled past the grace period, or unknown. This guards against accidents, not malice (the task URL has the admin credentials). Tests (`tests/task_db.rs`) pass the server with `Foreman::with_task_db_admin`.
- **`crates/wh-scorer`**: `ScorerService` consumes session completions and grades sessions of each factory scorer's `target` agent (only for tasks of that factory, deterministic `sampling_rate`). The judge is the same `AgentRuntime` (Claude Code) run with `AgentRequest.tools = Some(vec![])` in a temp dir. `judge.rs` is pure and unit-tested: it builds the prompt from rubric + task + agent prompt + final message + `git show <commit>` + condensed transcript, and parses the trailing JSON `{"score","classification","rationale"}`. WorkHub computes `pass` from `pass_threshold`. Events go on `score-<id>`: the automatic id is UUIDv5(session, scorer) and `ScoreStarted` is appended with `NoStream`, so redelivery never grades twice. `wh score session` uses a fresh id (`manual`). On first start the consumer checkpoint jumps to the log head (no paid backfill), and `recover_interrupted()` fails dangling `ScoreStarted`. Scorer prompts are hashed into `factory_version`. Read model `score_results` (`wh_metrics::scores`).
- **`crates/wh-improver`**: self-improvement. Runs are requested by `ImprovementRequested` on `proposal-<id>` (human via CLI/API, or `tick()`: factory `improvement.triggers` once per (trigger, factory_version) and `interval_hours` when there are ≥ `min_sessions` new sessions, both with deterministic `ProposalId::for_key` ids + `NoStream`, capped by `max_open_proposals`). `ImproverService` (consumer `improver:<factory>`) claims a request with `ImprovementStarted` at `Exact(1)` (at most once), builds the observation (`observe.rs`: per-version/stage metrics from read models, failures, scorer findings, review/gate/block feedback text from task streams, past proposals with reviewer comments, condensed example transcripts), and runs Claude Code (`acceptEdits`) in a worktree of the factory's git repo on branch `wh/proposal/<id>`. It may only edit files under the factory file's directory; WorkHub then requires the answer JSON (`prompt.rs`, pure + unit-tested), validates `Factory::load` on the worktree, requires a changed `factory_version`, commits, and records `ProposalCreated` (diff, files, proposed version) or `ImprovementSkipped`/`ImprovementFailed` (branch deleted). `commands.rs` (shared by CLI/API): `decide` (reject needs a comment, which the improver reads next time), `apply` (cherry-pick onto the factory repo's current branch, then `ProposalRolledOut`); `detect_rollouts` marks approved proposals live when the loaded factory has their version (hand-merged). A running foreman keeps the old factory until restarted. Read model `proposals_view`; `session_facts.stage_outcome` (from `StageExited`) gives reject rates; `wh_metrics::proposals::version_stats` is the before/after view. Integration tests use a fake runtime that edits the worktree.
- **`crates/wh-bench`**: benchmarks. A suite (`benchmarks/*.yaml`, `suite.rs`, pure + unit-tested) lists cases: a task, where agents work (the factory repo, another `repo`, or a `fixture` dir copied into a fresh git repo per case run), and a `check` run with `sh -c` on the finished task branch (exit 0 = pass, env `WH_BENCH_SUITE_DIR`/`WH_BENCH_CASE` so hidden checks live in `benchmarks/checks/`). Suites live outside `factory/` so the improver cannot edit the yardstick. A run (`bench-<id>`) loads the suite's factory at a `git_ref` (detached worktree under `$WH_DATA_DIR/bench/<run>/`), creates each case as a task with `TaskCreated.benchmark` set, and drives it inline with `Foreman::for_benchmark` + `drive()` (gates auto-approved, reviewer `benchmark`). The live foreman ignores benchmark tasks (`Scope`). Claim/recovery follows the improver: `BenchmarkRequested` then `BenchmarkStarted` at `Exact(1)`; `wh bench run` appends both at once. `BenchmarkStarted.pid` keeps startup recovery away from runs of a live process. **Benchmark data must stay out of production metrics**: `AgentDispatched.benchmark` → `session_facts.benchmark_run` / `tasks_view.benchmark_run`, and every live aggregate (dashboard, stats, `version_stats`, improver observe/triggers) filters `benchmark_run IS NULL`. Scorers skip benchmark sessions. Add that filter to any new live query. Read model `benchmark_runs` + `benchmark_cases` (`wh_metrics::benchmarks`).
- **`crates/wh-github`**: GitHub through the `gh` and `git` CLIs only (no webhooks). `github:` in factory.yaml (`wh_factory::Github`) is opt-in: without it tasks complete locally as before. With it, `decide` returns `Action::Ship` after the last stage (behind `ship_gate` if set, as a gate on the pseudo stage `SHIP_STAGE` = `"ship"`, which is reserved), and the foreman calls `wh_github::ship`: push `wh/task/<id>` (no force), find an open PR with `gh pr list --head` or `gh pr create` → `TaskShipped`. Failure → `TaskBlocked{stage: "ship"}`; resume with that stage ships again without re-running stages. Benchmarks never ship. `TaskStatus::Shipped` = waiting on the PR. `GithubService` (in `wh foreman`/`serve --foreman`, `--no-github` to skip, `wh github sync` once) polls `tasks_view` rows with `pr_state = 'open'` via `gh pr view --json …`, diffs against what the task stream already has (`poll::Seen`/`poll::observe`, pure + unit-tested) and appends every new `PrReviewed`/`PrChecksCompleted`/`PrMerged`/`PrClosed` of one poll in a **single** `Exact(version)` append (the foreman only acts on the head). The fold collects `pr_feedback` only while `Shipped` (and checks only for the pushed commit); `decide` turns it into a rework of `github.rework_stage`, counted in `pr_rework_loops` against `max_rework_loops`. `PrMerged` → `Done`, `PrClosed` → `Blocked`. **Merge conflicts**: `mergeable == CONFLICTING` (never `UNKNOWN`) → `PrConflicted{base, commit}`, once per head commit, only while `Shipped` on the pushed commit. With `github.conflict_gate`, `decide` first requests a gate on the pseudo stage `CONFLICT_STAGE` = `"conflict"` (reserved; reject → blocked, resume = approval). Then `Action::ResolveConflict` runs `rework_stage` with `RunSpec.merge`: the runner fetches `<remote>/<base>` and runs `git merge --no-commit` (never rebase) before the agent, quotes the conflicts in the prompt, fails the session if markers remain, and commits the merge itself. `TaskState.conflict` lasts until that stage succeeds and counts in `pr_rework_loops`. The guarded `conflict` gate arms in `decide` must stay before the generic gate arm. Issue intake: task id `TaskId::for_external("github:<repo>#<n>")` + `NoStream`. Tests (`crates/wh-foreman/tests/github.rs`) use a fake `gh` shell script (`Foreman::with_gh`, `Gh::new(path)`) and a bare repo as the remote; never call real GitHub from tests.
- **Drafts and the task tree**: `TaskCreated.draft` (CLI/UI/API default; GitHub intake, benchmarks and `wh run` start right away; old events = false) keeps a task in `TaskStatus::Draft` until `TaskActivated` (`commands::activate`, optionally the whole subtree). `TaskCreated.parent` / `TaskMoved{parent}` build a tree: `commands::move_task` walks the new parent's ancestors on the event streams under an advisory lock and refuses cycles. `TaskMoved` does not update `TaskState.last`, so `decide` still acts on the last pipeline event. Read model `tasks_view.parent_id`; `queries::children` / `descendants`.
- **`crates/wh-api`**: axum API under `/api`. Human commands (create, start, move, gate, resume, cancel) live in `wh_api::commands` and are shared with the CLI: they validate against the folded `TaskState` and append with `Exact(version)`, so a stale decision returns 409. Reads come from `wh_metrics::queries` (projections), except task/session event timelines, which read the stream directly. `Live` + `/api/events/stream` is the SSE feed: one LISTEN task publishes the head `global_seq` on a `watch` channel, and each client keeps its own cursor and reads the log itself (supports `Last-Event-ID`, `?after=`, `?task=`). Without `--auth` it acts as `$USER` and refuses to bind a non-loopback address. With `--auth` (`auth.rs`) every route but `/api/health` and `/api/auth/*` needs a session: users in `users` (argon2id, `wh user ...`), sessions in `auth_sessions` (only the sha256 of the cookie token is stored), cookie `wh_session` HttpOnly + SameSite=Strict (+ Secure for an https `--public-url`), per-client lockout after 5 failed logins, and mutating requests with a foreign `Origin`/`Sec-Fetch-Site` are refused. Handlers take `Extension<CurrentUser>` and record it as the actor. These two tables hold credentials, not read models. Tests drive the router with `tower::ServiceExt::oneshot`.
- **Self-update** (`wh_api::system`, local `wh serve` without `--auth`): the UI's "Update & restart" pulls `origin/main` (fast-forward only; the checkout must be on `main` and clean), rebuilds `wh` and `web/dist`, runs `wh db migrate`, drains (`wh_core::Drain`: the foreman holds new events unhandled, so they are redelivered after the restart, and waits for accepted stage runs; "Restart now" skips the wait), then `exec`s the new binary with the same arguments. Offered only when the running binary is in `<cwd>/target/`. Scorer/improver/bench runs are not drained. `boot_id` in `GET /api/system` changes on each start so open tabs reload; `index.html` is served `no-cache`.
- **`deploy/`**: production. A multi-stage image (`deploy/Dockerfile`: wh + web/dist + Claude Code + git + gh on node:22-bookworm-slim) runs `wh serve --auth` as a compose project (`deploy/docker-compose.yml`, own Postgres) behind the server's existing nginx and Cloudflare. Agents run inside that container with the worktree sandbox. `deploy/README.md` is the runbook.
- **`web/`**: React 19 + Vite + Tailwind v4 + shadcn/ui (add components with `npx shadcn@latest add <name>`), TanStack Query, react-router. `AuthGate` (`src/components/AuthGate.tsx`) shows the login form when `/api/auth/me` says auth is on and there is no user; any 401 sends you back to it. One `EventSource` (`src/lib/live.tsx`) invalidates queries on each event. Types for API responses live in `src/lib/api.ts`; keep them in sync with `crates/wh-api/src/dto.rs` and `wh_metrics::queries`.
- **`crates/wh-cli`**: the `wh` binary. Writes go through `EventStore::append` (commands → events). Reads come only from projections.
- The `wh` CLI pool allows 20 connections because every following consumer (5 projections, SSE, foreman, scorer, improver, bench worker) holds a LISTEN connection (the GitHub poller does not; it runs on a timer); adding consumers to `wh serve`/`foreman` may need more.
- `migrations/` is embedded at compile time via `wh_eventstore::MIGRATOR`. Add new files and never edit applied ones. After adding a migration, run `cargo build` then `wh db migrate` before running other commands. Otherwise projections fail with "column does not exist". New fields on existing events need `#[serde(default)]` so old events still decode.

New components from the design (foreman, runner, scorer, improver, api) become new `crates/wh-*` crates following the same pattern: consume events through `Subscription`, emit events through `EventStore`.
